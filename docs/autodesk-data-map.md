# Autodesk Data Map — Forma Risk Radar

Authoritative mapping from every risk metric in the product specification to a concrete Autodesk
source, or to an explicit statement that no such source exists.

**Status of this document:** it is the contract between the product specification and the ingestion
layer. If a metric is not in a table here, it has not been sourced. If a row says *Not currently
available*, no amount of implementation effort will produce it from the documented platform.

---

## 0. Naming, scope and reading rules

### 0.1 Which "Forma" this is

Autodesk renamed **Autodesk Construction Cloud (ACC)** to **Forma**, effective **2026-03-24**. The
developer doc set is now titled **"Forma APIs"** and lives at `/en/docs/acc/v1/`, but **the base
paths were not renamed**: they remain `/construction/…`, `/cost/v1/…`, `/bim360/…` and
`/data-connector/v1/…`.

This is **not** Forma Site Design (the former Spacemaker product) at `/en/docs/forma/v1/`. Forma Site
Design has no Issues, RFIs, Submittals, Forms, Construction IQ or Data Connector and is entirely out
of scope for this product. The distinguishing test is the hub identifier: ACC-now-Forma hubs use a
bare GUID; Forma Site Design uses `pro_…` identifiers.

Configure the ACC/Forma hub as the bare GUID `<ACC_ACCOUNT_ID>`; Data Management adds the `b.`
prefix only at its own call boundary.

### 0.2 The three provenance labels, used literally

Throughout this document, and throughout the codebase (`ValueKind` in
`src/lib/canonical/types.ts`), exactly three things can be true of a number:

| Label used here | Meaning | `ValueKind` in code |
|---|---|---|
| **(a) documented behaviour** | Stated in current official Autodesk documentation. Holds for any tenant. | — |
| **(b) requires-validation** | Seen during per-account Data Connector validation. Not documented; public examples omit tenant identifiers and populations. | — |
| **(c) our own derivation** | Forma Risk Radar computed it. Autodesk asserts nothing about it. | `application-derived` |

An Autodesk-computed value passed through unchanged is `autodesk-provided` and carries
`autodeskTerm`. **"Construction IQ Quality Risk" is an Autodesk value. "Derived Risk Exposure Index"
is ours.** Never the reverse, never blended, never renamed to look official.

### 0.3 Classification vocabulary (exactly one per row)

| Classification | Means |
|---|---|
| `Direct APS API` | Available as a field or filtered count from a documented REST endpoint. |
| `Data Connector` | Available only as a column in a batch Data Connector extract table. |
| `Autodesk-provided metric` | Autodesk (usually Construction IQ) computed the value; we pass it through unchanged. |
| `Application-derived metric` | Forma Risk Radar computes it. Inputs may be Autodesk data; the number is ours. |
| `Inferred relationship` | Depends on the Relationships graph or another adjacency signal that carries no direction, type or causality. |
| `Not currently available` | No documented API or dataset supplies the required input. Do not build. |
| `Requires validation` | A source is documented or plausible but unproven against this account; blocked pending a live check in §10. |

### 0.4 Naming convention for Data Connector tables

The Data Connector *service group* is named `iq`, `issues`, `rfis`, `submittalsacc`, etc. Extract
files land as `<group>_<table>.csv` — so the documented `iq.issues_quality_risks` arrives as
`iq_issues_quality_risks.csv`. This document uses the **file/table form** (`iq_issues_quality_risks`)
because that is what the ingestion code sees. Both forms refer to the same object.

### 0.5 Scope and permission columns

APS OAuth scopes are stated at the granularity the doc set gives. Where a per-endpoint scope is not
published, the row states the scope family required by the enclosing service and the precise scope
set is carried as open validation item **OV-16**. Per-account validation required a user-context token
for Data Connector, which makes the identity model, not the scope string, the binding constraint.

### 0.6 Two global facts that constrain every row

1. **This is a snapshot-and-diff analytics application, not a real-time risk feed.** Autodesk
   supplies genuine risk *values* only through Construction IQ, only through batch Data Connector
   extracts, and the hub is hard-capped at **24 extract jobs per rolling 24 hours** (account *and*
   per-user). Everything labelled "velocity", "persistence", "concentration", "recurrence",
   "exposure" or "funnel" is our own derivation over our own persisted snapshots.
2. **Portfolio hygiene is a correctness requirement.** Exclude `Template Project`,
   `Training Project`, and `Demonstration Project` rows from production rollups. Every portfolio
   metric below assumes these are filtered out; without the filter hub-level numbers are misleading.

- All velocity, ageing/persistence, concentration, recurrence, exposure and conversion metrics.
- **Overdue and days-overdue for every module** — no server-side overdue flag exists anywhere in ACC.
- Any project-level **safety** risk value.

- Time-in-status for anything except RFIs (and RFIs only via the unvalidated `rfis_rfi_transitions`).

- The composite "High Risk Issues" reconstruction (four-criteria rule).

### 8.3 Mandatory disclosures shown alongside any Construction IQ value

- *"Not every issue that Construction IQ identifies as high risk may be a high-risk issue. Conversely, Construction IQ may not detect every high-risk issue."*
- `user_*` columns are **human overrides** and can disagree with the ML value in the same row — show which one was rendered.
- *"A project's risk level doesn't indicate whether it's well managed; instead it indicates that the project has a higher than normal risk level for that day."* Do not build a cross-project risk leaderboard from raw CIQ values without normalisation.
- *"cost impact and quality risk have been developed as separate models… issues may have a high cost impact with a low risk level, and vice versa."* Do not treat `cost_impact` as a proxy for risk.
- Construction IQ produces **no data at all** for non-English project data, or for project types outside Commercial / Healthcare / Institutional / Residential and Infrastructure→Transportation Building. **Absence must render as "Not Applicable", never as "low risk".**

## 9. Per-account validation requirements

All undocumented schemas, value domains, coverage dates, and relationship populations must be
validated independently for each configured account.

### 9.1 Construction IQ

Profile every `iq_*` table at activation time. Preserve Autodesk's raw literals, record the
runtime casing, keep `user_*` overrides separate from model predictions, and render missing table
populations as **Not Applicable** rather than zero or low risk. Undocumented enums must remain
runtime-discovered.

### 9.2 Operational fact tables

Profile status, assignment, priority, form-value, project-type, company-trade, location-depth, and
schedule-criticality fields per hub. Treat project-configured IDs and labels as tenant-local. Do not
publish or hardcode one account's distributions.

### 9.3 Presence and density

CIQ daily tables can behave as sparse change-logs, RFI transition tables may provide deeper history,
and clash or custom-attribute bridge tables may be absent or thin. Record coverage dates and row
presence explicitly, forward-fill only within validated bounds, and keep unavailable populations
distinct from zero.

### 9.4 Relationship graph

Discover domains, entity types, directionality duplicates, and deduplicated edge counts at runtime.
Every graph or funnel view must show its current sample size. A per-account validation population must
never become a platform default or a public example.

### 9.5 Operational validation

Before activation, verify token context, region routing, signed-download handling, table schemas,
pagination, and per-service rate limits against a controlled account. Keep identifiers and
population profiles in restricted operational records, outside the public repository.

## 11. Identifier normalisation

Applied **once, centrally**, in the ingestion layer. No provider, analytic or component may re-derive
an identifier.

### 11.1 Hub and account identifiers

| Context | Form | Example |
|---|---|---|
| Data Management (`/project/v1/hubs`, `/data/v1/…`) hub id | **`b.` prefix + GUID** | `b.<ACC_ACCOUNT_ID>` |
| Every ACC/Forma module API `accountId` | **bare GUID** | `<ACC_ACCOUNT_ID>` |
| Data Connector `/data-connector/v1/accounts/{accountId}` | **bare GUID** | `<ACC_ACCOUNT_ID>` |
| Data Connector extract column `bim360_account_id` | **bare GUID** | runtime identical to the customer-supplied "Forma Hub ID" in every table |

Rule: **strip `b.` on ingest, store bare, re-add `b.` only at the moment of a Data Management call.**
Never store both forms.

### 11.2 Project identifiers

| Context | Form |
|---|---|
| Data Management project id | `b.<guid>` |
| Hub Admin, Issues, RFIs, Submittals, Forms, Locations `:projectId` | bare GUID |
| Data Connector `bim360_project_id` and `projectIdList` | bare GUID |

### 11.3 Container identifiers — never synthesized

`containerId` is **not** interchangeable with `projectId` even when the two happen to be equal.

| Service | `containerId` source |
|---|---|
| Cost (`/cost/v1/containers/:containerId/…`) | the project GUID in practice — but a live doc contradiction persists (the field guide still says obtain it from Data Management). **Read it, do not assume it.** |
| Relationships v2 (`/bim360/relationship/v2/containers/:containerId/…`) | the **Docs** project GUID |
| Model Coordination v3 (`/bim360/modelset/v3/containers/:containerId/…`) | the **Docs** project GUID |
| Locations `treeId` | the literal string **`"default"`** — not a GUID |

**Rule: never synthesize a service container ID from a project ID.** In Autodesk's own sample, the
cost and submittals containers equal the project GUID but issues/rfis/markups/checklists share a
*different* one. Read each from `relationships.<service>.data.id` on the Data Management project
resource and cache it.

### 11.4 The Construction IQ join trap

Construction IQ tables are **prediction side-tables**. They carry no title, status, assignee, date or
company and are useless without `admin`, `issues`, `rfis` and `relationships` in the same extract.

| From | To | Notes |
|---|---|---|
| `iq_<issue table>.id` | **`issues_issues.issue_id`** | **`issues_issues` has NO column named `id`.** Joining `iq_*.id` → `issues_issues.id` returns an **empty set with no error** — a silent zero-row dashboard. Per-account validation confirmed that the PK column is `issue_id`. |
| `iq_rfis_*.id` | `rfis_rfis.id` | RFIs *do* use `id`. The asymmetry with Issues is the trap. |
| `iq_company_*.company_id` | `admin_companies.id` | |
| `iq_*.bim360_project_id` | `admin_projects.id` | |
| `iq_*.bim360_account_id` | `admin_accounts.bim360_account_id` | Constant across the extract. |

Applies to all of: `iq_issues_quality_risks`, `iq_issues_quality_categories`, `iq_cost_impact_issues`,
`iq_inspection_risk_issues`, `iq_issues_safety_risk`, `iq_issues_safety_hazard`,
`iq_issues_safety_observations`, `iq_design_issues_root_cause`,
`iq_design_issues_building_components`.

### 11.5 Other join rules that fail silently

| Rule | Why |
|---|---|
| **Join roles on `role_id` / `role_oxygen_id`, never on `name`.** | Predefined role names are **localised per request language** — the same role returns a different `name` depending on the caller's locale. |
| **Do not key company history on `admin_companies.name`.** | Deleted companies have `name` overwritten with `"removed at MMDDYYYY"`. Key on `id`. |
| **Persist clashes on `clash.id`, `loid`, `roid` — never on `lvid`/`rvid`.** | Version-scoped IDs are explicitly not stable across seed-file versions; clash IDs are documented stable across model set versions. |
| **Normalise issue status before unioning REST and DC.** | DC `issues_issues.status` has 13 documented values; the REST API has 9. |
| **Normalise Construction IQ casing, never severity.** | `iq_issues_quality_risks.risk` is lower case, `iq_cost_impact_issues.cost_impact` is capitalised, `iq_issues_safety_risk.safety_risk_category` is snake_case against a documented spaced enum. `severityFromConstructionIq` normalises casing only — it never promotes `high` to `critical`. `critical` is reserved for application-derived escalation. |
| **Forms question identity: `forms_native_form_values.field_id` / `field_id_v2` → `forms_layout_section_items.uid` / `field_id_v2`.** | Validate the join and profile layout-item coverage carrying `label`, `type`, `modifier`. Stability across template edits is **OV-08**. |
| **Relationships: match on the unordered pair.** | Rows appear in both directions (runtime). Deduplicate on a canonical sorted `(item1_id, item2_id)` key or every edge is double-counted. |
| **Locations: cache `nodeId → {name, path, depth}` permanently.** | Deletes cascade and unlink referenced objects with no tombstone; historical `location_id` values otherwise become permanently unresolvable. |

### 11.6 Region

Hub Admin does not auto-route. Resolve the region per hub **before anything else** by probing
`GET projects` with each `Region` value (200 = correct, 404 = wrong) and cache the result. Header names
differ by module: `x-ads-region` on Issues / Model Coordination / Relationships, `Region` on Hub Admin,
`region` on Cost, none documented on Submittals / Forms / RFIs. See **OV-15**.

Also: parse the `meta` block on every `GET /project/v1/hubs` call — `BIM360DM_ERROR` 401/403 appears
inside an otherwise HTTP-200 response, and naive status-code handling silently sees an empty hub list.
